## Verdict and ranked findings

**High 1: The prototype is not a reliable reachability reference.** Two `.content--clip { overflow: hidden }` rules remain at `docs/design/mockups.html:303,354`. Seven frames use them: Today light/dark/AX3, Goal light/dark and Caffeine light/dark. `.content` itself has no scrolling (`:50`); the fixed-height outer device clips overflow (`:45`). Thus removing the modifier alone is insufficient. AX3 visibly ends at Next up with the timeline inaccessible in the supplied capture (`/tmp/nutrition-astra-review/today-ax3-light.png`). Caffeine fits the supplied default-size capture, but its explicit clipping remains a smaller-screen/large-text risk, not a demonstrated default-size overflow. Fix before approving reference screenshots.

**High 2: Numerical and acceptance contracts conflict.** #36 says to preserve every wireframe number, while research §4 lines 146–154 gives 426/70/about 95 against the mockup's 490/80/about 90. Today, Ride, Week, Log and Ideas must change together. Retaining logged breakfast/lunch forces a different remaining allocation. Exact rounding and whether this is a morning plan or a mid-day replan are undecided. Do not certify a screenshot by reproducing inconsistent totals.

**Medium 3: Logging has no unambiguous persistence state.** Editable food rows coexist with “Save · logged at 15:24” and “on target” for 92/80 g and 20/15 g (`mockups.html:483–489`; `/tmp/nutrition-astra-review/log-light.png`). DESIGN.md Controls and SwiftUI mapping promise a short-lived Undo toast, without a durable recovery path (`:61,173`). The state model below resolves both; tolerance needs a product/rules decision.

**Medium 4: Explanations and multi-session navigation are incomplete.** Today’s code links to Ride (`mockups.html:428`), whose “Why GREEN today” button has no destination (`:470`, dark `:637`). DESIGN.md `:170` promises a dedicated destination. The Week rows all link to the same Ride, including rest days (`:477`, dark `:644`). A session screen cannot explain a day composed of several sessions, an evening transfer, or missing inputs.

**Medium 5: Native accessibility mapping needs explicit exceptions.** Unfilled code bars are outlined in DESIGN.md Carb codes (`:42`) and SVG (`mockups.html:396–397`), but mapped to 30%-opacity shapes (`DESIGN.md:147`). The one-line segmented pace picker (`:162`) and auto-dismiss Undo (`:173`) lack AX5 alternatives. Chart labels and readings need separate, navigable semantics instead of treating the whole readings grid as one element (`:175`). None of these are proven native bugs because SwiftUI does not exist yet.

**Medium 6: Beta journey coverage stops before key outcomes.** Recipe titles link back to the Ideas frame (`mockups.html:500`), only onboarding step 2 is drawn (`:410`), and DESIGN.md States does not specify the complete recipe-detail, saved-meal-edit, paywall, Health-unavailable or multi-session paths. #20 explicitly requires profile, screening/referral and first plan before paywall; #15 requires edits with correct totals. Content contracts are needed before implementation.

### Log draft, saving, saved and editing

Use one meal identity and revision throughout; sync/export status is independent of local save status. The scheduled slot time, actual eaten time, and save time are different fields.

- **Draft:** editable foods, amounts, units and “Eaten at 15:24”; title identifies meal slot. Button “Log meal”. No logged check/lock. Switching meals preserves or explicitly discards the draft. Empty/invalid entries cannot save; inline messages explain why.
- **Saving:** “Saving…”; guard repeated taps. Preserve input on failure: “Couldn't save this meal. Your entries are still here.” Action “Try again”. A server outage is not a local-save failure.
- **Saved detail:** read-only item summary, actual eaten time and “Logged at 15:24”; action “Edit meal”. Local-only status “Saved on this phone, syncs later.” Optional separate Health export failure must not imply the meal itself was lost. Toast “Pre-ride snack logged” with Undo after local durability is confirmed.
- **Editing saved meal:** title “Edit pre-ride snack”; retain original version until “Save changes”. Cancel returns to unchanged saved detail. Successful edit updates the same meal, not another entry; totals reflect the delta once. Copy “Meal updated”. Deliberate corrections are allowed despite automatic-replan protection.
- **Undo:** revert only the save/edit transaction it refers to, with clear handling if the meal has subsequently changed. Keep an accessible, explicit dismissal path and durable Edit/Delete in saved detail, so a short timer is never the sole recovery route. For an accessible beta, prefer a persistent inline confirmation with Undo and Dismiss over a timed overlay.
- **Automatic replan:** preserve actual logged quantities. Lock explanation: “Saved meals stay unchanged when your plan updates. You can still edit them.” Avoid announcing a misleading “locked” without this distinction.

Evidence: DESIGN.md Controls `:54,60–61`, States `:94–99`, SwiftUI mapping `:173`; #15 editing/totals criterion; #16 logged-values criterion. Apple recommends minimizing timed UI controls: [HIG Accessibility, Cognitive](https://developer.apple.com/design/human-interface-guidelines/accessibility#Cognitive).

### “On target” tolerance

Do not silently choose a clinical tolerance or preserve “on target” by widening a band until the current food fits. Default proposal until a reviewed band exists: neutral comparison, “92 g carbs · planned 70 g · 22 g above plan” and “20 g protein · planned 15 g · 5 g above plan”. Saving remains permitted; this is logging actual intake, not enforcing compliance. No success check or warning based only on exceeding a point target.

If the product retains “Within planned range”, require engine-supplied lower/upper bounds and display them alongside the amount (copy pattern: “Carbs {actual} g · planned range {lower}–{upper} g”). Specify inclusive boundaries, rounding, separate carb/protein bands, zero/missing targets and whether a summary requires both nutrients to pass. Show per-nutrient status when only one qualifies. Compare unrounded values consistently and avoid displayed rounding implying a contradictory state. A range without an approved policy is not ready for a numeric mockup. Evidence: `mockups.html:488`; research §4 distinguishes broad guideline ranges from chosen app defaults (`:113–144`).

### Daily explanation destination

A pushed, scrollable **“Why today's targets”** screen, opened from Today’s code, Week’s day detail and the session’s Why row. Show the date and code plus plain-language level, not just GREEN. Preserve originating navigation and selected date.

Content order:

1. **Summary:** daily carb/protein/fat targets, a concise primary reason and plan revision time. Calories appear only if the global switch is enabled. Explain that GREEN means a high-carb day, not health/safety success.
2. **Today's training:** chronological session rows with sport, start, duration, source, planned/completed status, and relevant engine inputs with provenance. Tap a row for that session’s before/during/after plan. Single-session Tuesday names the 1 h 45 threshold ride; multiple sessions show every contributor and the combined daily result.
3. **How the day was calculated:** engine-provided base, session estimates, look-ahead adjustment, clamp/band and final daily total. The canonical illustrative explanation is 210 g base + about 216 g estimated training cost = 426 g, about 6.1 g/kg, pending rounding agreement. Base is an algorithm input, not the same concept as 210 g already eaten. Separate guideline source from the app’s interpolation/allocation choice.
4. **Across meals:** already logged intake, remaining budget and before/during/after allocations. Show that during-session fuel counts toward the day. On multi-session days identify shared recovery/preparation meals once; disclose overlap constraints instead of double-counting. If allocation cannot fit the daily policy, show an explicit unresolved-plan state rather than negative portions. This requires an engine conflict policy, not a design-only fix.
5. **Looking ahead:** tomorrow's session, why it affects tonight, the amount moved and both affected dates. A rest day can still fuel tomorrow. Explain changes without rewriting meals already eaten; distinguish moved allocation from added demand. Do not invent the unresolved cross-day accounting policy.
6. **Inputs and limits:** weight and timestamp, provider inputs and sync freshness, coach override, gut-trained cap, assumptions and missing fields. Manual/no-power example: “No planned power data. Targets use the guideline range for this session.” If essential inputs prevent calculation, show “Add weight” or another specific action, not a fabricated result. Cached plan: “Based on your plan from {time}”.
7. **Rule/source details:** expandable source title/year/link per calculation; explicitly label estimates. “Update workout” and “Review inputs” route to the relevant editor. Include a change explanation on revision.

Evidence: #16 reasons, #17 rule/source requirement, #18 look-ahead/rest days; DESIGN.md `:170`; research §4 `:129–144`. This structure answers §9’s transparency, plan-change and schedule complaints without presenting a technical debug log.

## 3. SwiftUI feasibility and accessibility audit

Common contract for every component: support the full Dynamic Type range through AX5 without capping text or shrinking to fit. Use `Font.custom(...relativeTo:)`, content-driven heights, and scaled nontext metrics where needed. AX3 CSS is illustrative, not proof of native AX5. Use actual bundled font names and verify tabular digits; DESIGN.md `:138` explicitly leaves them unchecked. Controls have a minimum 44 pt hit region per this design, with no overlapping invisible hit areas. Read VoiceOver in task order; do not combine a parent so aggressively that its child actions disappear.

Increase Contrast variants must be resolved in native assets/styles, including dark AMBER ink; CSS `color-mix` percentages alone are not an exact Swift color recipe. Choose explicit resolved colors and a consistent sRGB or P3 policy and remeasure native composites. DESIGN.md `:106–121` includes clipped sRGB approximations, so prior contrast ratios are not automatic native evidence. Reduce Motion disables app-owned movement and repeated animation; let native navigation respect the OS rather than promising to eliminate every system transition. Keep Paper surfaces for content; use native `TabView`/`NavigationStack` and safe areas for iOS 26 chrome. Do not rebuild the HTML tab capsule or paint opaque custom backgrounds over system navigation. These are proposed implementation rules; no runtime behavior is verified.

**Carb-code tags and bar glyph: small custom, worthwhile.** Three shapes plus text; use explicit fill versus outline per Carb codes, not faint solid bars. Scale the glyph; let the header wrap and keep the word visible at AX5. VoiceOver label “GREEN, high carbohydrate day”; hide decorative individual bars. Increase Contrast retains word/outline distinction and prescribed dark-AMBER ink. No motion needed. Tags stay content, not glass navigation buttons. Cheaper alternative if glyph maintenance fails: text badge plus explicit “high/moderate/low”; don't drop the word. Evidence: DESIGN.md `:40–47,65–78,146–147`.

**Meters: standard ProgressView with a small custom style, low risk.** Numeric actual/target remains primary; display under/over amounts even if graphical fill is clamped to 0…1. Missing/zero target gets a textual unavailable state, not division. Stack pairs and labels at AX sizes. One VoiceOver nutrient element states actual, planned and remaining/above, not duplicate percentage announcements. Strengthen track/border per Increase Contrast; no fill animation under Reduce Motion. Put meters in scroll content with native tab insets. Native default ProgressView plus labels is the cheaper fallback. Evidence: DESIGN.md `:56,65–77,148`; Today numbers `mockups.html:430–433`.

**Next up: standard composition, low risk.** VStack of title, time, targets and two actual buttons. At AX5 stack actions vertically and wrap the countdown; no fixed card height. VoiceOver reads context then independently reachable “Log pre-ride snack” and “Ideas for pre-ride snack”; avoid continuously announcing countdown changes. Strong text/button contrast; no animated card arrival or countdown under Reduce Motion. Card remains Paper2 and scrolls above the native tab bar. Cheaper alternative is a section with two labelled actions, not a bespoke interactive whole-card control. Evidence: DESIGN.md States `:91`; `mockups.html:435–439`.

**Timeline and Ride lanes: custom layout on standard containers, moderate risk.** Use LazyVStack rows; switch time rail/Grid to time-above-content at AX sizes. No decorative connector is essential. VoiceOver says time, meal/session, targets or actuals and saved status; navigation stays a separate action. Shared meal allocations appear once. Increase Contrast affects dividers and saved icons; Reduce Motion prevents animated reorder and preserves focus/scroll when a plan changes. Use native NavigationLink and push; no fixed tab-height calculations. Cheaper alternative: chronological List sections with time headers. Evidence: DESIGN.md `:149–150`, AX sizes; #16/#17.

**Week list: standard List with adaptive custom rows, low risk except routing.** At AX5 day/tag then full workout summary and grams; multiple workouts cannot be squeezed into one truncated title. VoiceOver includes date, number of sessions, day code, grams and look-ahead reason. Increase Contrast uses stronger separators and explicit selected/today words; Reduce Motion avoids animated target reshuffles. Keep native list scrolling/navigation under glass. All dates open a day detail, with session links therein; rest days open the daily explanation. This is cheaper and clearer than a custom seven-column calendar. Evidence: DESIGN.md `:74,151,163`; `mockups.html:477`; #18.

**Pace picker: standard at normal sizes, risky as a mandatory one-line segmented control.** Use four short segments where they fit. At AX sizes replace with a native Picker destination or four checkmarked list rows, including full “percent of body weight per week” labels and recommendation. VoiceOver exposes selection and resulting estimate; announce once after recomputation. Increase Contrast and Reduce Motion largely use native behavior, with static estimate updates for the latter. Native form rows fit Liquid Glass sheets; don't recreate segmented geometry or force tab-label typography. This native list is the cheaper accessible alternative. Evidence: DESIGN.md `:162,174`; #37.

**Caffeine chart: standard Swift Charts marks, custom semantic model; moderate/high complexity.** Layer ride RectangleMark behind AreaMark/LineMark; distinct dashed/solid RuleMarks for last-call/bedtime; PointMarks identify dose events with their actual times and mg labels. Define whether marker y is baseline (dose event) or modeled body amount; dose mg is not the body's mg at that instant. Label axes with units and next-day dates. Keep line/point/rule styles distinguishable under Increase Contrast; no curve drawing, pulsing or morphing under Reduce Motion. Chart is content under system navigation; no glass plot surface. Cheaper alternative: LineMark plus a dose/event list and key readings, omitting area fill and on-plot annotations. Retain the quantitative alternative. Evidence: DESIGN.md `:164–175,179–181`; Caffeine screenshot; [Apple chart descriptor documentation](https://developer.apple.com/documentation/swiftui/view/accessibilitychartdescriptor(_:)).

**Profile list: standard insetGrouped List, low risk.** Allow multiline row titles and a trailing status that moves below at AX5. Native Toggle exposes Show calories state; VoiceOver announces the Connections count in the row and tab badge without duplicate decorative badges. Increase Contrast separators/backgrounds use resolved tokens; no animated badge bounce under Reduce Motion. Preserve native tab/navigation glass and list insets, accepting differences from the HTML. No custom alternative is cheaper. Evidence: DESIGN.md `:59,155,168–169`.

**Sheets: standard sheet/Form/Picker/DatePicker, low risk if heights are flexible.** Medium/large detents for normal sizes, large presentation for accessibility text or keyboard-intensive content. Scroll form, visible Cancel/Save, labelled decimal field with unit, keyboard dismissal and inline validation reachable by focus. Increase Contrast uses native fields plus custom-text validation contrast; native Reduce Motion transitions, no extra scaling. Evidence: DESIGN.md `:172,174`; `mockups.html:345–348`; [Apple adoption guidance](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass).

**Toasts: custom and avoidably risky.** A timed bottom HStack can overlap floating tabs, lose Undo before VoiceOver reaches it and truncate at AX5. Prefer an inline, multiline confirmation region with Undo/Dismiss; saved meal detail remains the durable fallback. If an overlay survives, place it with safe-area-aware layout, stack actions, avoid stealing focus, announce once and prevent dismissal while interacting. Use opaque high-contrast tokens; no slide animation with Reduce Motion. Never position at a hard-coded HTML tab height or add another glass capsule over the native bar. Evidence: DESIGN.md `:173`; [Apple HIG timed-interface guidance](https://developer.apple.com/design/human-interface-guidelines/accessibility#Cognitive).

### What counts as a match

Exact: fixture values/units, content, selected states, provenance, meaning of code, hard-filter behavior, accessible action availability and data-state identity. Required: no truncation of essential data, no overlaps, full scroll/keyboard reachability, minimum hit targets, and correct hierarchy/reflow. Not required: pixel-identical HTML status bar, custom tab capsule, font rasterization, default list insets, system sheet geometry or Liquid Glass blur. These are native-owned. Document intentional platform differences in the PR with side-by-side named captures. After approving the first native baseline, use image diffs on the same OS/device/settings to detect regressions; inspect differences rather than accepting a global percentage threshold that can hide a missing button or digit. Mask only nondeterministic system chrome, never content or warning text.

Screenshot matches do not prove accessibility or persistence. Pair them with manual VoiceOver traversal/actions, chart exploration/readings, contrast measurements on actual assets, keyboard checks and tests for saves/undo/replans. Accessibility Inspector is useful but not a substitute for exercising the flow. Apple specifically recommends testing custom elements and system chrome across accessibility settings: [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass).
